# Task Manager — React + Express + PostgreSQL + Redis

A full-stack task manager. Users register, log in, and manage their own tasks:
create, view, edit, change status, delete, and search, filter, sort and page
through them. PostgreSQL is the source of truth; Redis caches read queries and
is invalidated on every change.

No Docker, no ORM magic beyond Prisma, no microservices: one React app and one
Express API.

## Architecture

```text
                 React (Vite)
                    │  REST / JSON, JWT in Authorization header
                    ▼
              Express API (Node.js)
     routes → controllers → services → repositories → Prisma
                    │
             ┌──────┴──────┐
             ▼             ▼
        PostgreSQL        Redis
     source of truth   cache only (optional at runtime)
```

| Layer | Responsibility |
|-------|----------------|
| `routes/` | URL + HTTP method, middleware chain (auth, validation, rate limit) |
| `controllers/` | Read validated input from `req`, call a service, send the response |
| `services/` | Business rules: auth, ownership, cache-aside reads, invalidation |
| `repositories/` | All Prisma queries. Every task query is scoped by `userId` |
| `validators/` | Zod schemas for bodies, params and query strings |
| `middleware/` | JWT auth, validation, rate limiting, request logging, central errors |

## Installation

### 1. PostgreSQL

Install PostgreSQL (Windows installer from postgresql.org, `brew install postgresql`, or
`apt install postgresql`), make sure the service is running, then create two databases:
one for the app and one for the integration tests.

```bash
psql -U postgres -c "CREATE DATABASE task_manager;"
psql -U postgres -c "CREATE DATABASE task_manager_test;"
```

### 2. Redis

Redis has no official native Windows build. Pick one:

| Platform | Command |
|----------|---------|
| Windows (WSL Ubuntu) | `sudo apt update && sudo apt install -y redis-server` then `sudo service redis-server start` |
| Windows (native) | Install [Memurai](https://www.memurai.com/) (Redis-compatible) and start its service |
| macOS | `brew install redis && brew services start redis` |
| Linux | `sudo apt install -y redis-server && sudo systemctl start redis-server` |

Check it: `redis-cli ping` → `PONG`. WSL 2 forwards `localhost:6379` to Windows, so
`REDIS_URL=redis://localhost:6379` works from Windows Node.js.

### 3. Backend

```bash
cd backend
npm install
cp .env.example .env            # then edit .env (see below)
npx prisma migrate dev          # creates tables + indexes, runs `prisma generate`
```

> an `allow-scripts` warning, run `npm approve-scripts @prisma/client @prisma/engines prisma`
> followed by `npm rebuild`.


## Database

### Schema

```text
users                               tasks
-----                               -----
id            uuid  PK              id          uuid  PK
name          varchar(100)          user_id     uuid  FK → users.id (ON DELETE CASCADE)
email         varchar(255) UNIQUE   title       varchar(200)
password_hash text (bcrypt)         description text NULL
created_at    timestamp             status      enum TODO | IN_PROGRESS | COMPLETED  (default TODO)
updated_at    timestamp             priority    enum LOW | MEDIUM | HIGH             (default MEDIUM)
                                    due_date    date NULL
                                    created_at / updated_at
```

### Migrations

```bash
npx prisma migrate dev --name <change>   # dev: create + apply a migration from schema changes
npx prisma migrate deploy                # prod/CI: apply existing migrations only
npx prisma generate                      # regenerate the client (migrate dev does this too)
npm run prisma:seed                      # reset demo users' tasks (runs in a transaction)
```

### Database indexes

Every task query has `WHERE user_id = $1`, so `user_id` leads each composite index.
PostgreSQL can then find one user's rows *and* use the second column for filtering or
ordering in the same index scan.

| Index | Serves | Why |
|-------|--------|-----|
| `users(email)` UNIQUE | login, register duplicate check | Created by the unique constraint, so no extra index is needed |
| `tasks(user_id, created_at)` | default list (Newest/Oldest), recent tasks, FK lookups | The most common query. It also covers the foreign key, so `ON DELETE CASCADE` doesn't scan the whole table |
| `tasks(user_id, status)` | status filter, dashboard `GROUP BY status` | Status is the most-used filter |
| `tasks(user_id, due_date)` | "Due date" sort | Lets the sort read rows in order instead of sorting them all |

Deliberately **not** indexed:
- `priority`: only 3 values. A per-user priority filter matches roughly a third of that
  user's rows, and scanning the `(user_id, …)` index is already cheap.
- Separate single-column `status`/`priority`/`created_at` indexes: never used without
  `user_id`, and every extra index slows down writes.
- Search (`ILIKE '%term%'`) can't use a B-tree index. If you need search at scale, add a
  `pg_trgm` GIN index or PostgreSQL full-text search.

### Transactions

Single-statement writes are already atomic, so they don't use a transaction. Ownership is
enforced inside the write itself (`UPDATE … WHERE id = $1 AND user_id = $2`), so there's no
gap between "check owner" and "write". `prisma.$transaction` is used where several writes
must succeed or fail together: the seed script upserts a user, deletes their tasks and
recreates them as one unit. Any future multi-record operation should do the same.

## Redis caching

Cache-aside, implemented in `src/services/cache.service.js` and `task.service.js`.

**What is cached** (per user): task-list pages, single tasks, dashboard stats.

### Key strategy

```text
tasks:user:<userId>:version                          integer, no TTL
tasks:user:<userId>:v<version>:list:page:1:limit:10:status:TODO:priority:all:search:redis:sort:createdAt:desc
tasks:user:<userId>:v<version>:task:<taskId>
tasks:user:<userId>:v<version>:stats
```

Keys are built from the **validated, normalised** query (defaults applied, search
lower-cased), so `?page=1` and `?` share a cache entry, and unknown query parameters can't
fragment the cache.

### Flow

```text
GET /api/tasks?...
  ├─ read user's version from Redis
  ├─ HIT  → return cached JSON                       (X-Cache: HIT)
  ├─ MISS → query PostgreSQL → SET key EX ttl → return   (X-Cache: MISS)
  └─ Redis down → query PostgreSQL directly           (X-Cache: BYPASS)
```

Every task response carries an `X-Cache` header, so you can watch the cache in the
browser dev tools or with `curl -i`.

- **Cache hit**: the response comes from Redis and PostgreSQL isn't queried at all (an
  integration test spies on Prisma to prove this).
- **Cache miss**: PostgreSQL answers, and the result is stored for `REDIS_CACHE_TTL` seconds.
- **TTL**: a short TTL (60s by default) is the safety net: even if an invalidation were
  lost, stale data lives for at most one TTL.
- **Invalidation**: `POST`, `PATCH` and `DELETE` write to PostgreSQL first, then
  `INCR tasks:user:<id>:version`. One atomic command makes every list, task and stats key
  for that user unreachable, and the old keys simply expire. This avoids slow `SCAN` + `DEL`
  over many keys. It's also race-safe: a request that read version 4 just before a write
  can only store its result under v4, which nobody reads any more. Other users' caches are
  untouched.
- **Fallback**: the Redis client fails fast (`enableOfflineQueue: false`) and reconnects in
  the background. Every cache call is wrapped: if Redis is down or a command errors, reads
  count as misses and writes are skipped, so the API keeps serving from PostgreSQL. The
  outage is logged once, not per request. `/api/health` reports `"status": "degraded"`.
- **Missed invalidations**: if a task changes while Redis is unreachable, the `INCR`
  can't be sent. The cache service records that user, bypasses the cache for them, and
  replays the `INCR` when Redis reports `ready` again. So if Redis comes back with its old
  data intact, that stale data is never served. The record lives in process memory: if the
  API restarts during the outage, the short TTL is the remaining safety net.

Try it:

```bash
TOKEN=$(curl -s -X POST localhost:5000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"Password123"}' | node -pe "JSON.parse(require('fs').readFileSync(0)).data.token")
curl -si "localhost:5000/api/tasks?status=TODO" -H "Authorization: Bearer $TOKEN" | grep -i x-cache   # MISS
curl -si "localhost:5000/api/tasks?status=TODO" -H "Authorization: Bearer $TOKEN" | grep -i x-cache   # HIT
redis-cli keys 'tasks:user:*'
```

## API

Base URL: `http://localhost:5000/api`. Protected endpoints require
`Authorization: Bearer <token>`.

Response envelope:

```json
{ "success": true, "data": { } }
{ "success": true, "data": [ ], "pagination": { "page": 1, "limit": 10, "total": 25, "totalPages": 3 } }
{ "success": false, "message": "Validation failed", "errors": [{ "field": "title", "message": "Title is required" }] }
```

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| GET | `/health` | – | Liveness + dependency status |
| POST | `/auth/register` | – (rate limited) | Create account → `{ user, token }` |
| POST | `/auth/login` | – (rate limited) | Log in → `{ user, token }` |
| GET | `/auth/me` | ✔ | Current user `{ id, name, email }` |
| GET | `/tasks` | ✔ | List own tasks (paginated, cached) |
| GET | `/tasks/stats` | ✔ | Dashboard counts (cached) |
| POST | `/tasks` | ✔ | Create a task |
| GET | `/tasks/:id` | ✔ | Get one own task (cached) |
| PATCH | `/tasks/:id` | ✔ | Update title/description/status/priority/dueDate |
| DELETE | `/tasks/:id` | ✔ | Delete → `{ id }` |

### `POST /auth/register`

```json
{ "name": "Mathan", "email": "mathan@example.com", "password": "Password123" }
```

Password: 8–72 characters, at least one letter and one number. Email is trimmed and
lower-cased. `201` → `{ user: { id, name, email }, token }`. Duplicate email → `409`.
`passwordHash` is never selected in responses.

### `POST /auth/login`

`{ "email", "password" }` → `200 { user, token }`. A wrong password and an unknown email
both return the same `401 Invalid email or password`, and both take the same bcrypt time,
so there's no account enumeration.

### `GET /tasks`

| Param | Values | Default |
|-------|--------|---------|
| `page` | ≥ 1 | `1` |
| `limit` | 1–100 | `10` |
| `status` | `TODO` `IN_PROGRESS` `COMPLETED` | all |
| `priority` | `LOW` `MEDIUM` `HIGH` | all |
| `search` | ≤ 100 chars, case-insensitive match on title or description | – |
| `sortBy` | `createdAt` `updatedAt` `dueDate` `priority` `title` | `createdAt` |
| `sortOrder` | `asc` `desc` | `desc` |

Filtering, searching, sorting and pagination all happen in PostgreSQL. Priority sorts
LOW < MEDIUM < HIGH. Tasks without a due date sort last. `createdAt` and `id` act as
tie-breakers, so pages stay stable.

### `POST /tasks` / `PATCH /tasks/:id`

```json
{ "title": "Learn Redis", "description": "Implement Redis caching", "priority": "HIGH", "dueDate": "2026-12-01" }
```

`title` is required on create. PATCH needs at least one field. `status` defaults to
`TODO` and `priority` to `MEDIUM`. `dueDate` is `YYYY-MM-DD`, and `null` clears it (as does
an empty description). Unknown fields such as `userId` are rejected with `400`: the owner
always comes from the JWT.

### `GET /tasks/stats`

`{ total, todo, inProgress, completed, highPriority }`

### `GET /health`

```json
{ "success": true, "status": "ok", "database": "connected", "redis": "connected", "uptime": 42 }
```

Returns `status: "degraded"` (still `200`) when Redis is down, and `503` with
`status: "error"` when PostgreSQL is down.

### Status codes

`400` validation / malformed JSON · `401` missing, invalid or expired token · `404` task not
found **or owned by another user** (existence isn't revealed) · `409` duplicate email ·
`413` body over 100 kB · `429` too many auth attempts · `500` unexpected (generic message;
stack only outside production)

## Security

- Passwords are hashed with bcrypt (12 rounds) and never returned or logged.
- JWT is HS256 with an explicit algorithm allow-list (rejects `alg: none`), an expiry, and
  the user id in `sub`.
- `authMiddleware` protects every task route. The user id is never read from the request body.
- Ownership is checked in SQL (`WHERE id AND user_id`), and other users' tasks return 404.
- All input is validated with Zod (strict objects, enums, length limits, UUID ids).
- Helmet security headers, CORS limited to `CORS_ORIGIN`, and a 100 kB JSON body limit.
- Login and register are rate limited per IP.
- Structured pino logs with the Authorization header and password fields redacted. Request
  logs contain only method, URL, status and duration.
- Secrets live only in `.env`, which is git-ignored.

Known trade-offs (fine for this project, worth knowing):
- The JWT is stored in `localStorage`, which is simple but readable by any XSS. A production
  hardening step would be an `httpOnly` cookie plus CSRF protection.
- Logout is client-side (the token is discarded). A token stays valid until it expires; a
  Redis deny-list keyed by token id would add server-side revocation.

## Frontend

- **Routes**: `/login`, `/register`, `/dashboard`, `/tasks`, `/tasks/new`, `/tasks/:id`,
  `/tasks/:id/edit`. Unauthenticated users are redirected to `/login` and returned to the
  page they asked for after logging in.
- **Auth state** (`AuthProvider`): `user`, `token`, `isAuthenticated`, `loading`. A saved
  token is verified with `/auth/me` on page load. Any `401` signs the user out.
- **API layer**: one Axios instance (`services/api.js`) adds the token and reads
  `VITE_API_URL`. Components call `authApi` and `taskApi`, never Axios directly.
- **Task list**: search (debounced), status, priority and sort filters live in the URL query
  string, so they survive reloads and back/forward. Every filter becomes a backend query
  parameter. Pagination shows Previous / numbered pages / Next.
- **UX states**: loading spinners, empty states ("No tasks found. Create your first task."),
  error alerts with Retry, disabled buttons while submitting or deleting, success messages,
  and a confirmation dialog before delete.
